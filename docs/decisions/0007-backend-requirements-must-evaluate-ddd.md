# 0007：涉及后端的需求必须先做 DDD 影响评估

## 状态

已接受。

## 背景

项目已经接受“后端采用模块化 DDD 分层”的架构决策，但如果后续需求进入时没有把 DDD 评估前置，执行时仍然容易出现这些问题：

- 先写功能，再事后解释应该属于哪个 domain。
- 把协议处理、用例编排、领域规则和基础设施细节混在一起。
- 新增接口或表结构时，没有同步判断是否需要新增仓储契约、领域对象或跨领域编排。
- DDD 规则只停留在架构文档，未真正成为需求处理流程的一部分。

项目需要把“符合 DDD”从实现偏好升级为需求入口阶段的显式检查项。

## 决策

- 只要需求、Bug、重构或配置变更涉及后端，主 Agent 必须在 Harness 草案或执行计划里主动补充 DDD 影响评估。
- 该评估至少回答：
  - 属于哪个顶层 domain。
  - 落在哪一层：`interface`、`application`、`domain` 或 `infrastructure`。
  - 是否需要新增或调整仓储契约、领域服务、command/query handler、migration 或适配器。
  - 是否存在跨领域协作，以及是否仍由 application 层同步编排。
- 若现有文档无法支撑上述判断，应先更新 `docs/architecture.md`、`docs/backend-ddd.md` 或新增决策记录，再进入实现。
- 后端 Agent 的交接和主 Agent 的集成检查，都要显式核对该评估是否成立。

## 影响

- DDD 分层从“后端实现约束”升级为“后端需求入口约束”。
- 未来每个涉及后端的需求都会在草案阶段暴露领域归属和分层落点，减少实现期返工。
- 架构文档、执行计划和角色交接会更早承载后端设计意图，而不是依赖聊天上下文。

## 不做的事

- 不要求每个后端改动都新建 domain。
- 不为了形式统一而把简单逻辑过度抽象。
- 不把 DDD 评估变成冗长模板；重点是提前回答关键边界问题。
