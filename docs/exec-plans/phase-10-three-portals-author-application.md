# Phase 10：三端拆分与作者申请升级

## 状态

已完成并通过当前轮验收。

说明：

- 最终验收结果采用同域不同入口路径，而不是最早草案中的“三个不同端口”默认设想。
- 当前正式入口为：
  - 读者主站：`/`
  - 作者端：`/author`
  - 后台端：`/admin`
- 主站导航不再暴露后台入口；后台账号与前台读者/作者账号仍保持完全隔离。

## 验收结论

本阶段已完成以下关键目标：

- 前台用户体系与后台运营体系已彻底分离。
- 前台角色已收敛为 `reader` / `author`。
- 后台角色已收敛为 `super_admin` / `reviewer`。
- 读者申请作者、后台审核申请、后台用户列表直升作者均已实现。
- 只有作者本人可以上传、发布、修改书籍及维护章节。
- 后台不再负责书籍正文和章节内容编辑，但可进行运营治理，如分类、站点设置、作者审核、推荐值调整。
- 旧数据兼容不再作为实现前提，允许按新模型初始化。

## 背景

当前系统默认把公开阅读、作者创作和管理员运营放在同一个前端站点中，角色模型也主要围绕 `guest`、`user`、`admin` 展开。这种结构对 MVP 足够，但已经开始限制后续产品演进：

- 读者、作者、管理员的入口和导航语义混在一起。
- 普通登录用户既承担“读者”身份，又被默认赋予创作入口，不利于权限收束。
- “成为作者”缺少明确的申请、审核和状态流转。
- 不同使用场景共用一个端口，不利于后续部署、访问控制和独立验收。
- 后台管理员和前台读者/作者混在同一套账号语义里，不利于安全隔离和运营分工。

用户提出的新方向是：

1. 系统改为读者端、作者端、后台端三个不同端口。
2. 注册用户默认先是读者。
3. 读者通过申请并获批后，升级为作者。
4. 后台管理员与读者/作者不是同一套账号，后台存在超级管理员和审核人员。

## 目标

1. 公开阅读体验收敛到独立读者端。
2. 作者创作能力收敛到独立作者端。
3. 管理员运营能力收敛到独立后台端。
4. 前台用户体系与后台运营体系彻底分离，不共享账号身份和登录入口。
5. 注册用户默认只有读者权限，不再默认拥有创作权限。
6. 新增“作者资格申请 -> 后台审核 -> 角色升级”的完整流程。
7. 后台支持从申请记录审核升级，也支持在用户列表中直接将读者提升为作者。
8. 在不拆后端微服务的前提下，完成前端入口、权限和契约的重构准备。

## 非目标

- 本轮不默认拆分为三个后端服务，后端仍优先保持单体 API。
- 不引入作者等级、签约、收益、草稿箱、审核发布、定时发布等完整作者平台能力。
- 不引入多组织、多租户、多站点隔离。
- 不在本轮实现复杂审批流，如多级审批、审批会签或消息中心。
- 不默认改造为基于子域名的生产部署方案；本轮先按“不同端口”规划和验证。
- 不要求兼容旧业务数据；如进入实现，可直接清空现有数据并按新模型初始化。

## 默认实现假设

- 读者端和作者端共用同一套前台用户体系；后台端使用独立的运营账号体系。
- 三个端口可以共用同一个后端服务，但认证入口、会话载荷和权限判断按“前台用户”和“后台运营账号”两条链路分开。
- 当前前端仓库继续共存，但会拆成三个独立 Web 入口或三个独立构建目标，共享基础组件、样式资产和 API client。
- 注册成功后的默认角色从“可直接创作的普通用户”调整为“读者”。
- 作者是前台用户体系中的一种账号能力，经审核后获得，不单独注册第二个前台账号。
- 后台运营账号不允许直接登录读者端或作者端；前台读者/作者也不能直接登录后台端。
- 后台至少存在两类运营角色：
  - `super_admin`：创建和管理审核人员。
  - `reviewer`：处理作者申请，并可在用户列表中直接提升读者为作者。
- 管理后台中的运营账号不等于书籍作者；后台不负责发布书籍、上传书籍或修改书籍内容。
- 作者申请默认采用人工审核；审核结果至少包含“通过”与“拒绝”。
- 拒绝后允许再次申请，但同一用户同一时间只允许存在一条待审核申请。

## 需求理解校准

### 术语净化映射

- `读者端` -> 面向游客与登录读者的公开阅读门户
- `作者端` -> 面向获批作者的创作工作台
- `后台端` -> 面向运营账号的审核与管理后台
- `申请变成作者` -> 作者资格申请与审核流转
- `管理员不互通` -> 前台用户体系与后台运营体系账号隔离
- `超级管理员` -> 可创建审核人员的后台最高权限账号
- `审核人员` -> 处理作者申请、查看用户列表并提升作者的后台运营账号
- `不同端口` -> 独立 Web 入口与独立本地运行/验收目标

### 核心对象与关系

`FrontUserAccount`

- 本质：`identity` 域聚合根
- 生命周期：注册 -> 读者 -> 作者
- 不变量：
  - 用户名唯一
  - 密码只保存哈希
  - 前台用户只能处于 `reader` 或 `author`
  - 账号角色必须来自服务端受控状态流转

`OperatorAccount`

- 本质：`identity` 域聚合根
- 生命周期：由超级管理员创建 -> 审核人员或超级管理员 -> 禁用或删除
- 不变量：
  - 后台运营账号不与前台用户账号复用
  - 运营角色只能处于 `super_admin` 或 `reviewer`
  - 只有 `super_admin` 可以创建审核人员

`AuthorApplication`

- 本质：`identity` 域内实体
- 归属：引用 `FrontUserAccount`
- 生命周期：提交 -> 待审核 -> 已通过 / 已拒绝
- 不变量：
  - 同一用户同一时间最多一条 `pending`
  - 已通过申请不能重复通过
  - 审核动作必须由后台运营账号执行

`PortalAccess`

- 本质：派生能力，不单独持久化
- 规则：
  - `guest` / `reader` 可访问读者端
  - `author` 可访问读者端和作者端
  - `reviewer` / `super_admin` 可访问后台端
  - 后台运营账号不进入读者端和作者端

`Book`

- 本质：`book` 域聚合根
- 既有约束延续：
  - 书籍归属作者
  - 章节与书籍的一致性规则保持不变
- 新约束：
  - 只有作者可以发布、上传、修改和维护自己的作品
  - 后台运营账号不直接创建、上传、修改或删除书籍内容

### 流程走查（含异常与并发）

`读者申请成为作者`

- 前置条件：用户已登录，当前角色为读者
- 触发主体：读者
- 核心动作：提交作者申请，系统记录申请状态为 `pending`
- 后置影响：作者端入口仍不可用，但用户能看到申请状态
- 异常分支：
  - 已有待审核申请时拒绝重复提交
  - 已是作者时拒绝申请
  - 表单不完整时返回校验错误
- 并发场景：
  - 双击提交或并发请求只能创建一条待审核申请

`后台审核作者申请`

- 前置条件：存在待审核申请
- 触发主体：审核人员或超级管理员
- 核心动作：批准或拒绝申请
- 后置影响：
  - 批准：用户角色升级为作者，作者端解锁
  - 拒绝：用户仍为读者，可按规则重新申请
- 异常分支：
  - 申请不存在或已处理时返回冲突或不存在
  - 非后台运营账号调用返回无权限
- 并发场景：
  - 两个审核人员同时审核同一申请时，只允许一个审核成功

`后台用户列表直接提升作者`

- 前置条件：目标前台用户当前为读者
- 触发主体：审核人员或超级管理员
- 核心动作：在后台用户列表中直接把读者提升为作者
- 后置影响：
  - 若存在该用户的待审核申请，可同步标记为“已通过（后台直接提升）”
  - 若不存在申请，也允许直接升级
- 异常分支：
  - 目标用户不存在时返回 `NOT_FOUND`
  - 目标用户已是作者时返回幂等成功或冲突，具体行为待确认
  - 非后台运营账号调用返回无权限
- 并发场景：
  - 同一用户被同时审核和直接升级时，只允许一次状态迁移成功

`作者访问作者端`

- 前置条件：用户已登录且角色为作者或具备作者能力
- 触发主体：作者
- 核心动作：访问作者端入口并管理自己的作品
- 后置影响：沿用现有作品管理、上传、章节维护链路，但入口从读者端剥离
- 异常分支：
  - 未登录时跳转登录
  - 已登录但仍为读者时展示“申请成为作者”引导或审核状态

## 影响范围

- 产品：角色体系从“普通用户直接可创作”调整为“读者申请后成为作者”，且后台运营账号与前台用户账号完全分离。
- UI：前端从单站点改为三端入口，新增作者申请、后台申请记录、后台用户列表与审核人员管理页面。
- 前端：路由、导航、认证守卫、入口工程、页面布局与 API client 均受影响。
- 后端：身份体系拆分为前台用户与后台运营账号两类，作者申请用例、审核用例、直接升级用例和门户访问判断需调整。
- API：前台登录态、后台登录态、作者申请、申请查询、后台审核、后台用户列表与运营账号管理接口都要调整。
- 数据库：前台用户角色字段、后台运营账号表、作者申请表、索引与初始化策略需要更新。
- 测试：需要新增角色流转、三端访问控制、申请审核、用户列表直接升级和回归 smoke。
- DevOps：本地开发、Docker Compose、构建脚本和端口分配需要更新。
- 安全/权限：必须明确三个端口的访问边界、两套账号体系和越权防护。

## 契约变化

### DDD 影响评估

- 领域归属：
  - 前台读者/作者账号、后台运营账号、作者申请与审核流转，默认归属 `identity` 域。
  - 作品归属、章节维护和作者对自己书籍的操作，继续归属 `book` 域。
  - 上传 `.txt` 与封面文件的存储和校验，继续归属 `upload` 域。
- 分层落点：
  - `interface`：新增前台登录接口、后台登录接口、作者申请、申请状态查询、后台审核、后台用户列表直升作者、审核人员管理等接口。
  - `application`：编排“提交申请”“审核申请”“直接升级作者”“创建审核人员”“按身份体系返回门户能力”等用例。
  - `domain`：
    - `identity` 需要新增前台账号与后台运营账号的边界、作者申请实体、角色流转规则和防重复申请规则。
    - `book` 需要把“只有作者可以发布和修改自己的书籍，后台运营账号不介入书籍内容编辑”的规则收紧为显式能力判断。
  - `infrastructure`：新增后台运营账号表、作者申请表、唯一索引、仓储实现，并调整两套认证载荷或查询逻辑。
- 仓储契约：
  - `identity` 需要新增作者申请仓储契约。
  - `identity` 前台用户仓储需要支持角色升级、申请状态查询和审批写入。
  - `identity` 后台运营账号仓储需要支持超级管理员创建审核人员、运营账号鉴权和状态维护。
- 跨领域协作：
  - 作者申请获批时，由 `application/identity` 同步协调“申请状态更新 + 用户角色升级”。
  - 后台直接在用户列表提升作者时，由 `application/identity` 同步协调“用户角色升级 + 可选的申请状态回写”。
  - `book` 域不直接依赖申请实体，只消费“当前 actor 是否具备作者能力”这一结果。
- 架构建议：
  - 本轮不新增 `authoring` 顶层领域，避免把“创作入口”误建模为独立业务域。
  - 本轮也不单独新增 `backoffice` 顶层领域，先在 `identity` 域内显式区分“前台账号”和“后台运营账号”；若后续后台运营能力继续扩张，再评估拆分。

### API

#### 前台身份与登录态

调整：

- `POST /api/auth/login`
- `GET /api/auth/me`

响应建议从单一 `role` 扩展为更明确的前台账号能力描述，至少包含：

- `role`：`reader` / `author`
- `portals`：允许访问的门户列表，如 `["reader"]`、`["reader", "author"]`
- `authorApplicationStatus`：`none` / `pending` / `approved` / `rejected`

#### 后台登录态

新增：

- `POST /api/admin/auth/login`
- `GET /api/admin/auth/me`

响应建议至少包含：

- `role`：`super_admin` / `reviewer`
- `portals`：固定包含 `["admin"]`

#### 作者申请

新增：

- `POST /api/author-applications`
  - 认证：需要登录，且当前角色为读者
  - 用途：提交作者资格申请
  - 请求建议：
    - `penName`：可选，作者显示名或笔名策略待确认
    - `reason`：可选，申请说明
  - 响应建议：
    - `applicationId`
    - `status`
    - `submittedAt`

- `GET /api/author-applications/me`
  - 认证：需要登录
  - 用途：查询当前用户的作者申请状态

#### 后台申请审核

新增：

- `GET /api/admin/author-applications`
  - 认证：仅后台运营账号
  - 用途：分页查看作者申请列表
  - 查询参数建议：
    - `status`
    - `page`
    - `pageSize`

- `PATCH /api/admin/author-applications/{applicationId}`
  - 认证：仅后台运营账号
  - 用途：审核申请
  - 请求建议：
    - `decision`：`approved` / `rejected`
    - `reviewNote`：可选

#### 后台用户列表与直接提升

新增：

- `GET /api/admin/users`
  - 认证：仅后台运营账号
  - 用途：分页查看前台用户列表
  - 查询参数建议：
    - `q`
    - `role`
    - `page`
    - `pageSize`

- `PATCH /api/admin/users/{userId}/author-role`
  - 认证：仅后台运营账号
  - 用途：直接将前台用户从读者提升为作者，或回写申请状态
  - 请求建议：
    - `action`：`promote_to_author`
    - `reviewNote`：可选

#### 审核人员管理

新增：

- `POST /api/admin/operators`
  - 认证：仅 `super_admin`
  - 用途：创建审核人员账号

- `GET /api/admin/operators`
  - 认证：仅 `super_admin`
  - 用途：查看后台运营账号列表

- `PATCH /api/admin/operators/{operatorId}`
  - 认证：仅 `super_admin`
  - 用途：启用、禁用或调整审核人员状态

#### 作者端作品接口

调整建议：

- 现有 `/api/me/books`、`/api/me/books/upload`、作品编辑与章节管理接口继续保留，但权限从“任意登录用户”收紧为“作者本人”。
- 如果保留“我的作品”语义，读者访问时不再直接进入作品管理，而是进入申请引导或状态页。

#### 后台与读者端

- 现有面向内容管理的后台书籍、章节、上传接口在 Phase 10 中默认下线或迁移出后台端，不再作为运营账号能力保留。
- 读者端公开搜索、详情和阅读接口保持公开/登录要求不变，但不再暴露作者创作入口。

### 数据

#### 前台用户角色

调整建议：

- `users.role` 从 `user/admin` 调整为仅承载前台角色：`reader/author`
- 默认注册角色改为 `reader`

#### 后台运营账号

建议新增 `operators`

字段建议：

- `id`
- `username`
- `password_hash`
- `role`：`super_admin` / `reviewer`
- `status`：`active` / `disabled`
- `created_by_operator_id`
- `created_at`
- `updated_at`

#### 新增表

建议新增 `author_applications`

字段建议：

- `id`
- `user_id`
- `status`：`pending` / `approved` / `rejected`
- `pen_name`：可为空，是否落库取决于产品确认

- `updated_at`

索引与约束建议：

- `idx_author_applications_user_id`
- `idx_author_applications_status`

#### 迁移策略

- Phase 10 默认不保留旧数据，允许在实现前清空现有用户、作品、申请和后台账号数据。
- 数据初始化建议改为：
  - 重建前台用户表角色语义，仅保留 `reader/author`
  - 新建后台运营账号表，并初始化至少 1 个 `super_admin`
  - 清空旧的书籍、章节、申请及与旧权限模型强耦合的数据后，再按新规则导入或重新创建
- 若后续决定保留部分种子数据，应在实现前单独补一版重建脚本和初始化说明，而不是回退到兼容迁移路径。

### UI 状态

#### 读者端

- 保留：首页、搜索、详情、阅读、登录、注册
- 新增：
  - 作者申请入口
  - 作者申请状态页或账号页中的申请状态区
- 去除：
  - 直接面向所有登录用户的“我的作品”入口

#### 作者端

- 仅作者可访问
- 页面建议包含：
  - 作者首页或工作台
  - 我的作品
  - 上传小说
  - 新建小说
  - 章节管理
  - 账号设置
- 书籍发布、上传、基础信息修改和章节修改均只允许作者本人操作。
- 读者访问作者端时：
  - 未登录：跳转登录
  - 已登录但未获批：展示“申请成为作者”或“审核中/已拒绝”状态

#### 后台端

- 仅后台运营账号可访问
- 新增：
  - 作者申请审核列表
  - 作者申请审核详情或侧边编辑区
  - 前台用户列表
  - 超级管理员的审核人员管理页
- 去除：
  - 后台书籍发布、上传、编辑、章节维护能力
- 必备状态：
  - 加载态
  - 空状态
  - 审核成功态
  - 审核失败态
  - 无权限态

#### 三端入口

- 三个端口都需要稳定的未登录跳转、无权限提示和登录后回跳策略
- 三个端口都应避免把不属于当前门户的导航暴露给错误角色

## 角色分工

- 主 Agent：整理和更新 Harness 草案，等待用户确认后组织拆分与集成。
- 产品 Agent：确认角色模型、作者申请规则、数据重置口径和非目标。
- UI Agent：确认三端页面清单、导航、申请状态、审核状态和跨端跳转体验。
- 前端 Agent：设计三端入口工程、路由守卫、共享模块和页面重构策略。
- 后端 Agent：设计两套身份体系、角色升级、申请审核、直接提升作者、审核人员管理、数据重建脚本和 DDD 落点。
- 测试 Agent：补充申请流转、端口隔离、角色门禁和回归 smoke。
- DevOps Agent：调整 Docker Compose、本地开发命令和端口约定。
- Reviewer Agent：检查权限回归、数据重建风险、契约漂移和测试缺口。

## 验收标准

- 新注册用户默认是读者，不能直接访问作者创作能力。
- 读者端、作者端、后台端可在三个不同端口独立运行和访问。
- 读者可以提交作者申请，并能查看当前申请状态。
- 后台审核人员可以在申请记录中查看并审核作者申请。
- 后台审核人员可以在用户列表中直接将读者提升为作者。
- 超级管理员可以创建审核人员账号。
- 只有作者可以发布书籍、上传书籍、修改书籍基础信息和维护章节。
- 申请获批后，同一账号无需重新注册即可访问作者端，并能管理自己的作品。
- 申请被拒绝后，用户仍为读者，系统给出明确状态反馈。
- 现有公开阅读、搜索、详情和章节阅读能力不因三端拆分而回归损坏。
- 数据清空并按新模型初始化后，系统能稳定创建新的前台用户、后台运营账号、作者申请和作者作品。
- 非作者读者无法调用作品写接口，后台运营账号也无法调用书籍发布和修改接口，前台用户无法登录后台端，非后台运营账号无法调用后台审核接口。
