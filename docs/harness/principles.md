# Harness Engineering 原则

本项目将 Harness Engineering 用作 AI 辅助开发工作流。小说阅读网站本身不是 Agent 产品；Harness 用来约束 Agent 如何开发、验证和演进软件。

## 核心表述

人类掌舵，Agent 执行。

Harness 是仓库内的工程环境，用来让 AI 开发过程更可靠、更高效、更安全、更可追溯。

## REST 目标

### 可靠性

- 优先使用确定性命令，而不是依赖人工检查。
- 关键操作尽量设计为可安全重试。
- 实现前先捕获验收标准。

### 效率

- 入口文档保持简短并提供链接。
- 使用渐进式披露，而不是维护巨大的说明文件。
- 优先选择朴素、可检查的技术和明确契约。

### 安全性

- 管理员操作遵循最小权限。
- 校验上传文件，避免任意文件系统访问。
- 不把密钥写入源码或文档示例。

### 可追溯性

- 在 `docs/exec-plans/` 中记录实现阶段。
- 在 `docs/decisions/` 中记录已接受的取舍。
- 验证失败时，记录修复来自代码、测试、文档还是工具。

## 面向开发的 PPAF 闭环

### 感知

Agent 在编辑前阅读 `AGENTS.md`、当前执行计划、架构说明、产品规格和契约。

### 规划

Agent 将工作拆成有明确验收标准的小阶段。

### 行动

Agent 进行聚焦修改，并运行该阶段要求的命令。

### 反馈

Agent 使用构建、测试、冒烟检查和用户反馈来更新代码或 Harness。

## 设计原则

- 契约优先。
- 为失败而设计。
- 默认安全。
- 决策与执行分离。
- 让重要行为可以度量。
- 让重复失败推动 Harness 演进。

## 应放入 Harness 的内容

- 产品和架构文档。
- API 和数据契约。
- 执行计划。
- 验证命令。
- 安全和角色约束。
- 决策记录。
- 能捕获重复错误的脚本或测试。

## 项目协作 Skill

本项目推荐使用 `harness-agent-team` skill 处理复杂需求、Bug 和多角色协作任务。

使用时机：

- 需求或 Bug 输入较模糊。
- 影响产品、UI、前端、后端、测试等多个角色。
- 需要先生成或更新 Harness 草案，再等待用户确认。
- 需要按角色拆分任务并在最终集成时回填 Harness。

## 不应放入 Harness 的内容

- 冗长且无人维护的提示词堆积。
- 只存在于聊天记录里的隐藏需求。
- 对第三方产品品牌或资产的精确复制。
- 无法被发现、执行或验证的规则。
